# Fantasy Basketball (in-Claude analyzer and draft tool)

A self-contained fantasy basketball brain: no accounts, no APIs. `scripts/hoops.py` converts the projection table in `data/players.csv` into 9-cat z-score values and exposes rankings, punt builds, trade math, and a live snake-draft tracker. Your job is to run the right subcommands, then add the judgment the numbers don't carry — and to keep the data honest by refreshing it when stakes are real.

## Data honesty (read first)

`data/players.csv` is the research baseline (the pool is whatever the file holds — the live count is stamped in `data/roster_verification.json` and the deck manifest, never quote it from memory; 2025-26 per-game production, placements maintained by the daily sweep; method in data/RESEARCH.md, rebuilt 2026-07-11). It's a plain file; changing a row changes every ranking. Rows carry a `note` column — always surface these flags when recommending a flagged player. **Injury handling is mechanical (owner's rule)**: a note starting `out-` (season-ending injury) AND any `*-recovery` note (serious-injury recovery, e.g. missed last season) remove the player from every ranking and draft board automatically — recovery players are EXCLUDED, not discounted (owner ruling 2026-07-12: three arena drafts each stacked four discounted recovery stars; real 2025-26 recovery players delivered ~9% of games; "shift to healthy, available players"). `*-risk` applies a 0.78 downgrade (shown as `*` injury-adjusted values; calibrated vs real 2025-26 games played — see arena/results/findings_2026-07-12_overnight.md §8). During the daily refresh, encode injury news with exactly these note conventions — announced out-for-the-season → `out-<reason>`; recovering from serious injury with no confirmed full return → `inj-<reason>-recovery`; **re-entry due diligence**: when news confirms a recovery player is fully back and playing, re-tag `inj-<reason>-risk` (first season back) or clear the note — that is the only path back into the pool. **Note syntax is load-bearing (2026-08-09):** the tier is read from the note's LEADING tag only — everything from the first space or parenthesis onward is prose. `inj-achilles-risk (recovery on track)` is a RISK row; before 2026-08-09 that same note silently deleted the player from every board. Keep the tag first and the commentary after it. Never present bundled numbers as live stats; say they're projections.

**Mandatory daily refresh (owner's rule).** Every hoops.py command checks `data/freshness.json` and prints a stale-data banner if the data wasn't refreshed today. That banner is BLOCKING for you: on the first fantasy request of a new day, before delivering any analysis, (1) web-search current NBA rosters/trades, injury reports, and rotation news for the players that matter to the request (the user's roster, draft-relevant tiers, any player being evaluated); (1b) **POOL COMPLETENESS SWEEP (owner law, 2026-07-22)**: the refresh scope is ALL draft-relevant NBA players, not just names already in the pool — after each June NBA draft, add the incoming rookie class's consensus fantasy-relevant players (rows with landing team, `rookie-proj` estimates); year-round, add new signings, two-way conversions, and breakout candidates entering top-200 relevance the moment news makes them draftable. Enforcement is mechanical: append each class's consensus names to `MUST_HAVE` in `scripts/hoops.py` so `freshness --stamp` FAILS while any are missing (the 2026 class — Dybantsa, Peterson, Boozer, Wilson — was added under this law); (1c) **ROSTER VALIDATION LOCK (owner law, 2026-07-23)**: every pull cross-references pool team assignments against NBA.com/ESPN-sourced transaction records — sweep the official trade trackers (deadline recaps, offseason tracker), FA/signing trackers, and draft results covering the window since the last verified pull, and spot-verify any row that news, analysis output, or the user calls into question. Enforcement is mechanical (v2, hardened 2026-07-23 after the Hachimura miss — a quiet FA signing no headline sweep caught): every pull runs `python3 scripts/verify_rosters.py`, which cross-references EVERY pool row per player against NBA/ESPN official roster data and writes `data/roster_verification.json`; `freshness --stamp` HARD-FAILS unless that artifact is dated today with zero mismatches (`--force` bypasses only with the reason stated in `--note`). The script pulls all 30 rosters directly from ESPN's public API when the environment's network policy allows `site.api.espn.com` (the complete guarantee — recommend the owner enable this domain); until then it consumes `data/rosters_official.json`, an evidence file the pull populates from NBA/ESPN-sourced verification, honestly marked `fallback-partial`. FA rows are verified by absence. Why this is law: the 2026-07-11 baseline silently carried 11+ stale team rows from the February 2026 deadline window (AD, DLo, Garland, Harden, Zubac, Mathurin, Vučević, Simons, JJJ, Reid, Randle, Claxton) plus the Hachimura FA miss — incremental news-sweeps can never catch quiet transactions; (2) update the affected `players.csv` rows — team, stats, and `note` column; (3) record it: `python3 scripts/hoops.py freshness --stamp --rosters-verified "<sources>" --note "<what changed>"`. Only then run the analysis. (1d) **PUBLISH GATE / SLA (owner law, 2026-07-23)**: no data reaches a published artifact without same-day validation. The Draft Deck's embedded pool may ONLY be regenerated via `python3 scripts/build_deck.py` — a fail-closed pipeline that refuses unless (i) today's roster verification exists with zero mismatches, (ii) freshness is stamped today with the verification recorded, and (iii) the pool validates; it then machine-syncs the deck's data-pull stamp from `freshness.json`, verifies the injection round-trips byte-identical, and writes a build manifest into the file. Hand-editing the deck's embedded `PLAYERS` data, `BUILD_PULL`, or injection anchors is prohibited — if the pipeline refuses, fix the data, never the gate. **Republish freshness is part of the gate (owner incident 2026-07-27)**: the published Draft Deck renders only what the last `build_deck.py` run baked in — data pushed to any repo is invisible to it. A refresh that changes the pool is complete only when `docs/draft-deck.html` is rebuilt and republished to the EXISTING artifact URL the same day (header stamp reads "fresh today"), with the deck's `JUDGMENT` layer re-authored from that day's research in the same pass. A published deck whose `built` date trails the latest freshness stamp is a live defect, not cosmetic lag — the owner found the deck serving a 3-day-old pool on 2026-07-27 while both repos believed themselves current. (1e) **ROLE-REPRICE COUPLING (owner law, 2026-07-23)**: a roster fix is not complete until the role is re-priced. Every team-change, signing, waiver, or depth-chart-altering transaction found by a pull triggers a role review of (a) the moved player and (b) every teammate whose opportunity he changes — new usage share, minutes competition, starter/bench status. Strong evidence (beat-reported roles, contract signals, actual prior-season splits) reprices the `players.csv` projection line with the rationale recorded in the stamp note; directional-but-uncertain reads (unsigned FA destination, RFA standoffs, unresolved timeshares) go into the deck's judgment layer as per-player adjustments with a stated why — never silently left at the old context. Why this is law: the 2026-07-23 grind proved rosters and roles drift independently — 226/226 verified team rows still carried ~26 projection lines priced for teams the players no longer played for (Vucevic ranked #20 on a starter's line he lost; NAW ranked #118 on a pre-breakout line). If web search is unavailable, say so explicitly, deliver the analysis labeled as running on unrefreshed data, and do not stamp. **Boundary with the speed rule**: live-draft commands never print the stale banner and never trigger a refresh — staleness is checked once at `draft init`; if a draft crosses midnight, finish the draft and refresh after.

## Analysis commands

Run from the project root:

| Question | Command |
|---|---|
| Overall or punt rankings | `python3 scripts/hoops.py rank --top 30 [--punt "FT%,TO"] [--pos C]` |
| What does this roster look like | `python3 scripts/hoops.py profile --players "Name1,Name2,..." [--punt ...]` |
| Should I make this trade | `python3 scripts/hoops.py trade --send "A,B" --get "C" [--punt ...]` |
| Find a player / check the pool | `python3 scripts/hoops.py find <name-fragment>` |

Category convention: FG% and FT% are volume-weighted; TO is already inverted (positive z = fewer turnovers). +1.0 z ≈ one standard deviation above average.

## Live draft protocol

### Draft-night surface — read this before anything else (owner-set 2026-08-09)

**The published Draft Deck is the board and the ledger. The owner types every pick into it himself.** It owns the ranked Top-5, the single 🎯, and the draft state. Its ordering is the blend50 score — the only ordering with replay validation behind it (14/14 drafts improved, mean +11.6pp).

**`hoops.py` is NOT a second board.** Two surfaces ranking the same players by different objectives is how the system ended up with two #1s that disagreed on 19 of 26 owner turns, with nothing written to resolve it at a 45-second clock. `hoops.py` orders by punt-aware `adj_value`, which has never been validated against blend50. Its live role is now:

1. **The fallback board** if the deck is unavailable mid-draft. Then, and only then, its candidate order governs — say plainly that you are on the fallback.
2. **The analysis layer** the deck cannot supply — above all **punt coherence**, because the deck's ordering is punt-blind by design. This is the single most valuable thing you add: the deck ranks as if no punt were declared, so when the owner is in a punt build, the deck's #1 may sit in a punted category.
3. **The state-integrity layer**: `--expect`, UNKNOWN quarantine, collision halts, `resync`.

Reconcile the two through the deck's **Export/Import `draft_state.json`** buttons — the exact file `hoops.py` reads and writes. Never reconcile by hand-editing state.

If the deck and `hoops.py` disagree on the top candidate, **the deck governs** and you say so in one clause, naming the reason for the divergence (usually: the deck is punt-blind, or the deck's ΔECW half sees the room and `adj_value` does not).

### Live-turn I/O contract (owner-set 2026-08-10)

**The owner feeds the pick stream to Claude pick-by-pick, in addition to typing every pick into the deck himself.** Both surfaces see the same feed; neither reads the other's screen. Concretely:

- Every owner message during the draft is a feed for ONE `draft turn "..." --expect N` call (the SPEED RULE below). Claude never sees the deck's Top-5 or its margins and never asks for them mid-clock.
- At the owner's turn, Claude's card is the **complement**, not a copy, of the deck: punt/concession coherence, injury and rule flags, state integrity. The deck on the owner's screen governs the ordering; if Claude's order visibly disagrees with what the owner reads out, Claude says the deck governs and names the divergence reason in one clause.
- "The deck is unreachable" is a fact only the OWNER can declare (Claude cannot see his browser). If he declares it, Claude's card becomes the board and says so — the fallback path.
- Reconciliation between surfaces is by feed and RESYNC paste only, never by file transfer mid-draft; the deck's Export/Import is a between-sessions tool.

**Owner's league (layout confirmed 2026-07-12)**: 12 teams, 13-player rosters — PG, SG, G, SF, PF, F, C, C, Util, Util, BN, BN, BN = **156 total picks** (owner provides their draft slot closer to the season). The engine's feasibility guard matches the roster onto the eight positional slots (G takes PG/SG, F takes SF/PF, two C required); Util/BN take anyone. Deep-draft dynamics (owner's rule): through roughly the first ~120 picks (rounds 1–10) teams draft to fill position slots — weigh position need heavily there; from round ~11 (the util/bench tail), shift to best-player-available and category specialists that extend the user's leads or rescue winnable categories. **Init echo (ledger lesson #7, from the 2026-07-12 slot-9 practice)**: `draft init` prints teams × rounds = total picks — read that product back to the owner and get confirmation BEFORE pick 1; never discover the draft length at the end.

1. **Before the draft** — the user may say **"Prime for live draft"**: run the full pre-draft checklist in one shot — freshness status (refresh news + stamp if stale), pool validation, `draft init` with the user's slot, and confirm the response protocol (mirror lines, calculated candidate lines, SYNC/RESYNC) in a two-line ready message — plus one reminder to the user: **for common surnames (White, Murray, Ball, Bridges, Sharpe, Robinson, Thompson, Collins...), feed first initial + surname ("D White", "Jam Murray")** — surname-only feeds are the biggest live error source. Otherwise: confirm the user's slot (the layout is known — 13 slots, 156 picks) and whether they're committed to a punt build (offer `rank --punt` comparisons if undecided). Web-search for injury updates on likely first-two-round picks. **Consult arena intel — regenerate, don't trust what's on disk**: both intel JSONs are git-tracked (the 'gitignored' claim this line used to make was false — R4-F33/41) but go stale with every pool refresh or engine change, so regenerate both as part of priming (`python3 arena/arena.py slots --seasons 1500 --rotations 3 && python3 arena/arena.py cadence --drafts 60` — run inline, not backgrounded; measured ~76s, not the ~10 min this line used to claim), then read `arena/results/slot_intel.json` (which builds win from the user's slot) and `arena/results/cadence_intel.json` (expected tier/position drain between the user's turns — reach when the cadence says a tier won't survive the wait; wait when it will). **Read these as 2025-snapshot STRUCTURAL intel only** (snake rhythm, tier drain shape) — the arena runs on the frozen October-2025 pool, so they do not track the live board (audit F58). The old skip-condition was unexecutable: neither JSON carries a `generated_at` stamp, so "newer than the last pull" cannot be evaluated. And note the slot table's own bound: ~2-3 draws per cell, SE ~4pp, top-2 gap under 3pp at 10 of 12 slots — the best-strategy-per-slot line is near-arbitrary (F09). Cadence intel (a drain count) is far better estimated than slot intel. **Artifact parity check (R4-F28)**: fetch the published deck URL and confirm its build-manifest `built` date is >= the date of the last commit touching `docs/draft-deck.html` — a page older than the source is running retired code and must be republished before it governs anything. Then `python3 scripts/hoops.py draft init --teams 12 --size 13 --slot K` — and confirm the echoed total-picks product with the owner.
2. **During — SPEED RULE (owner's rule, non-negotiable)**: the user is on a 45-second pick clock and needs suggestions within seconds, so a live-draft turn uses **exactly ONE command**: `python3 scripts/hoops.py draft turn "Name; Name; my:Name"` — semicolon-separated picks in draft order, the user's own prefixed `my:`. It logs everything (snake attribution automatic, nicknames like SGA/KAT/Dame resolve, bad names are reported without aborting) and emits the complete decision card in ~50ms: candidates annotated with the user's weakest categories, per-category rank vs the field, position counts, and the top rival's head-to-head edge. **Verify-state-first (owner's rule, learned 2026-07-12 INC-1)**: a tool call whose result is lost still mutates state — never treat silence as "nothing happened." `--expect N` (the pick count you believe is logged) is STANDARD on every turn command — a per-feed state handshake: on mismatch it logs nothing and prints the state tail so you reconcile and resend only unlogged names. (Promoted from re-send-only to always-on after the 2026-07-12 Cowork verification.) **Hot rule**: from 3 picks before the user's turn, start composing the suggestion from the latest card so the recommendation posts within seconds of their clock starting. NEVER chain extra commands mid-draft (no separate best/matrix/status calls, no web searches, no CSV edits — the freshness refresh happens BEFORE the draft starts); `draft pick`/`--slot` remain for corrections between turns only. **Arena live-mode carve-out (codified 2026-07-12, 90-call zero-drift run)**: in `arena.py live` practice drafts, one turn = the empty-feed card call (`draft turn "" --expect N`) plus the `my:` log call, each with `--expect` — that documented two-call pattern counts as ONE command for this rule; only the card printed after the latest `live` call is authoritative.
3. **At the user's turn — calculated output only, NO confidence percentages (owner directive 2026-08-09)**. The `NN%` format is RETIRED. It had no calibration procedure and no anchor: across the only 45 recorded cards the top candidate never left a 50–88 band, the scale's own "95% = no contest" end was reached zero times (Wembanyama at pick #1 with a >4z gap drew 88), cards summed to 149–272, and the mandated "(coin flip)" tag was silently missed on 8 of the 32 turns its own rule fired. **Never emit a percentage, a confidence score, or an adjective standing in for one ("clear favourite", "slam dunk", "no-brainer"). Every number you print must be one you computed, in a stated unit.**

   The candidate list is **the deck's Top-5 on the owner's screen** (it carries the margin in expected categories won per week; you never see it — the I/O contract above). Your card is the complement, built from the ONE `draft turn` call, in this order:

   `Name (POS, NBA team) — val ±X.XX` + rule-triggered flags in brackets. **val is the card's printed adjusted value** (`*` = injury-adjusted at 0.78 — relay the star; the ± is just the value's sign). It is NOT "kept-z": the two differ by the 0.78 haircut on risk rows (R4-F09 — the original wording here mandated a number the one allowed command never prints). Category movement vs the field comes from the same card's `helps/hurts` line and vs-field ranks (⚠ feasibility, [3rd TEAM], [inj-*], [unsigned-fa-monitor], ⚠ LEAN).

   Then **one committed recommendation with the deciding quantity named**. If the deck's #1 and your punt-aware order disagree, say which you are taking and why in one clause. If two candidates sit within ~0.03 val of each other, say "near-tie on value" and let a flag break it — do not manufacture a distinction. (0.03 is the pool's measured median adjacent gap, 2026-08-10; the previous ~0.25 figure was transplanted from a retired display threshold in a different unit and fired at 12 of 13 board depths — R4-F10. September recalibrates this from replay data.) If the deck is unreachable, order from `draft turn` and say you are on the fallback board.

   **Recovery players are never candidates (owner ruling 2026-07-12, supersedes the recovery-concentration compounding rule)**: the engine excludes `*-recovery` players from every board — never recommend one, never work around the exclusion; if the owner explicitly names one, log the pick (the engine warns but obeys) and move on without relitigating. **Healthy tiebreak (codified 2026-07-12, arena-calibrated)**: when a healthy candidate sits within ~5% of a `*-risk` candidate's injury-adjusted value (the `*` number on the card — that is the reference), prefer the healthy player — risk-flagged players carry roughly double the weekly game-count variance, which is pure downside in H2H. This is a tiebreak, not a veto — but the carve-out is narrow (codified from the 2026-07-12 ×3 run): a flagged player escapes the tiebreak only by clearly winning on the adjusted VALUE number itself (outside the ~5% band); category fit alone never invokes it, or the carve-out would swallow the tiebreak in every near-tie. Order by punt-aware kept-z, best first. If the user asks "why", explain after picking, not before. **Winning potential overrides position balance (council-ratified 2026-07-11, 5–0)**: if a player clearly increases expected category wins — measured by gain in CONTESTED categories per the matrix, not raw total value — recommend them even if it overcrowds a position; surplus is playable at Util and is trade capital. Position enters the call only as (1) a hard feasibility check — never leave a required slot unfillable given remaining picks (the turn card warns) — and (2) a tiebreaker between near-equal candidates, where roster balance breaks the tie. Marginal value in already-locked categories counts for little; say so when it drives a demotion.
4. **Response protocol during drafts (owner's rule)**: when logging picks that are NOT the user's turn, reply with mirror lines ONLY (`✓ #N Player`) — no analysis, no prose. Full candidate cards fire exclusively when the user is on the clock. Recovery keywords, each ONE command (mechanisms added 2026-08-09): **SYNC** → `draft status --tail 6` (picks-logged count, the last six picks with numbers and teams, your next pick number, plus any UNKNOWN placeholders); **RESYNC:** followed by a pasted pick list → `draft resync "<paste>"`, which wipes the board and rebuilds it from the paste — snake attribution re-derives positionally, so `my:` markers are optional in a complete in-order paste. The prior board is kept at `draft_state.json.pre-resync` (NOT `.bak` — the one-generation `.bak` is overwritten by the rebuild itself, R4-F01); restore with `cp draft_state.json.pre-resync draft_state.json`. An empty paste is refused and clears nothing. Never rebuild a board by hand-editing state or by `draft init --force` plus a feed.
5. **Corrections and ambiguity (owner's rule, learned 2026-07-11)**: a re-sent already-drafted name in a bulk feed is skipped with a warning (no pick logged — overlapping feeds are safe); UNKNOWN placeholders are reserved for names matching nobody. NEVER infer a duplicate is a correction; corrections apply only via explicit pick numbers ("44- Herro" or `draft fix`), echoed before/after. Ambiguous names auto-resolve in the engine to the best available candidate with an "(assumed over ...)" flag — relay the flag, don't stall. Typos fuzzy-match automatically (Siakim→Siakam).
6. **Owner soft rules (both subordinate to winning potential)**: (a) avoid rostering a 3rd player from the same NBA team — the turn card tags candidates `[would be 3rd TEAM]`; surface the flag and let it break a near-tie, never veto a clear win; (b) when the roster leans heavily positional (the card's ⚠ LEAN flag, e.g. 7F vs 3G), surface the flag so the user can rebalance — again advisory, never above winning potential.
7. **Opponent intel on demand**: `draft rosters` lists every team; `draft vs --team N` gives a head-to-head category comparison (useful in H2H leagues to spot rivals' weaknesses and in the endgame to pick fights the user can win).
8. **Corrections**: `draft undo` reverses the last pick; `draft fix N "Name" [--slot]` corrects any logged pick. Numeric prefixes in `draft turn` ("44- Herro") auto-correct when the number matches an existing pick — but 3+ corrections in one batch halts as suspected numbering drift; run `draft status` and verify before resending.
9. If a drafted player isn't in the pool, `draft turn` logs an UNKNOWN placeholder automatically — snake attribution never drifts. Between turns (or post-draft), add the player's row to `data/players.csv`, then `draft fix N "Name"`. Never edit the CSV while the user is on the clock.

## Analysis rules

- **Commit.** One recommendation with the deciding factor named; alternatives get one line, not equal billing.
- **Punt coherence.** In a punt build, judge every pickup/pick by the KEPT categories; call out when a tempting player's value lives in the punted ones.
- **Full-tilt doctrine (owner ruling 2026-08-10).** The owner does NOT declare punts — "I only wait until the system calculates this and directs to full tilt when clear dominance over opponent rosters." Do not expect a `--punt` at init and never push for a declaration (measured: declaring cost −3.1 to −6.4pp on the corrected instrument, −5 to −11pp on the original — G1a). The operative duty is DETECTION: watch the turn card's vs-field ranks; when categories have gone effectively dead (rank ≥ 10 with the gap widening) while the build clearly dominates its kept core, SAY SO and direct the concession — name the dead categories, the kept core, and what full tilt means for the next picks. Until that signal is clear, draft balanced value.
- **Trade verdicts** combine the script's net z with roster fit: a negative-net trade can still be right if it consolidates strength into scarce categories the user is contesting. Say which consideration wins and why.
- **H2H vs roto**: z-totals map cleanly to roto; in head-to-head, weight swing categories (close weekly margins) and streaming flexibility more heavily.
- **Never invent live data.** Season stats, injury news, and schedules beyond the CSV come from web search, labeled as such.

## Edge cases

- **A drafted player is missing from the pool** → offer to add rows to `data/players.csv` for the missing players (same columns; estimates are fine if labeled in `note`).
- **Draft state exists from a previous session** (`draft_state.json` in cwd) → `draft status` first and confirm whether to resume or `draft init --force`.
- **Yahoo/ESPN integration requests** → this tool is deliberately offline; the user can paste rosters as text and you analyze via `profile`/`trade`. (A Yahoo OAuth client was removed from this repo — see git history — after Yahoo's portal refused fantasy API scope.)

## When NOT to use this skill

- General NBA chat (real standings, awards, career stats) → answer normally or web-search; no hoops.py call.
- Multi-option dilemmas the user wants formally deliberated ("council: should I punt assists?") → the claude-council skill owns the deliberation; use this skill to fetch the numbers it debates.
